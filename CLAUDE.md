# edward

Edward is a live dashboard for the Claude Code agentic workflow (`shoklah/gilead`, exported as `shoklah/roland`). It shows what the workflow's reporter, `scripts/workflow-report.py --json`, says about runs, steps, findings and spend.

This is a personal project, used as a playground for trying things and as a portfolio piece to show. The repo is public: it holds code and invented data only, and reads the real data at run time on the owner's machine. Design decisions are recorded in `docs/superpowers/specs/2026-11-09-live-dashboard-design.md`.

## Where freedom is allowed

- **Playground: technology choice, across the stack.** Frontend and backend frameworks, the ORM and migrations, charts, styling and build tooling are free ground for trying things. Each choice is recorded under `## Stack` below with one line on why.
- **Not playground: the data rules.** Privacy, facts only from the reporter, the server's `Host` checks, raw exports kept, and tests follow the workflow's rules (TDD, simplest first, reuse before writing, match the codebase), whatever the technology.

This repo is also the testbed for the workflow's design focus: design processes and skills are tried here first, and what earns its keep goes to the workflow repo as a change request.

## Stack

The stack is final; the component kit, the graphical libraries and the mockups keep evolving, one library per job at a time, and a swap is its own small task.

- **TypeScript end to end** (backend, frontend, import validation): one set of types runs from checking the reporter's JSON on import through the API to the charts, which guards "facts agree". The reporter itself stays Python, run as a separate process.
- **Final:** Node LTS, Hono, Drizzle over SQLite (`better-sqlite3`) with its migrations, zod, React with Vite, TanStack Query and Router, Tailwind, Vitest, Storybook, Playwright, pnpm workspaces (`shared`, `server`, `web`), GitHub Actions on fixtures only.
- **Evolving, current choice:** shadcn/ui for components (its Radix base, lucide icons and `cn` come with it), React Flow for Home's workflow diagram only (the run page draws its graph itself), ECharts for charts (through `echarts-for-react`), TanStack Table for tables (headless, so it renders into shadcn/ui's table with the API's own row types), `@axe-core/playwright` for the accessibility checks.
- **Labeller:** `@anthropic-ai/sdk` for the labeller's calls, through the official SDK.

## Design conventions

- The look is the root `DESIGN.md` (night glass, with liquid glass as its light pair); screens are designed and reviewed against it.
- `DESIGN.md` is the look and wins where it and the kit's floor disagree; a code convention that contradicts it is the one to change.
- Screens are agreed as mockups with invented data before the plan; the approved ones live in `docs/design/<date>-<topic>/`.
- Every component has Storybook stories on invented fixtures for its empty and full states, and a component that fetches data also for loading and error; a story with an interaction test is the UI's failing test.
- Screens are checked on fixtures with Playwright screenshot comparisons and axe accessibility checks.
- Charts are written with the `dataviz` skill loaded.
- Show, don't tell: a screen's explanatory text passes the test in `DESIGN.md`'s Do's and Don'ts (necessary, not redundant with what is drawn, not covering for a design gap), and a spec says why each one stays.

## Code conventions

- The app is edward: lower-case as a wordmark, "Edward" in prose. The `@cwd` package scope (its initials), the data folder (`platformDefaults` in `packages/server/src/config.ts`), the launchd label (`LABEL`) and the systemd unit (`UNIT`, both in `packages/server/src/agent.ts`) keep the project's first name.
- The data is personal (project paths, branch names, session IDs, costs, finding text): never commit real data, never put it in fixtures, never publish it publicly. Fixtures are invented.
- `workflow-report.py` is the only parser of the run log and the transcripts: when the dashboard needs a new fact, it goes to the workflow repo as a change request, never parsed here.
- This repo never edits the workflow repo or the template; they are a reference and the data source.
- Relative imports carry their `.ts` extension and type-only imports use `import type`; packages export their TypeScript sources, with no build step.
- The reporter's JSON schema lives in `packages/shared/src/report.ts`: every field is `.nullish()` (a `z.unknown()` one `.optional()`) unless the loader can't work without it; it validates the fields the dashboard reads plus those kept for slice 2's pages, any other field is left out, so it is stripped, and whether an unread field's drift should fail an import is the owner's call.
- A time from the reporter becomes a `Date` only through `parseTime` in `packages/shared/src/week.ts`, which reads a zone-less time as UTC as the reporter does, never through `new Date` or `Date.parse`.
- A fixture's `totals` agree with its runs and sessions by the reporter's rules (`week_rows`, `scoreboard`, `run_time`, `skill_totals`, `model_totals`, `advisor_facts`, `offer_totals`, `context_rows`): for `weeks`, per week start date, `runs` by path and `cost` as the sum of the priced cost of the runs with `models`, null when none has them; for `context`, per week, over the units whose `context` isn't null, a run in its record's week and a session in its start's, `calls`, `tokens`, `tool_results` by class and `sweeps` by kind summed, `max_tokens` the max and `units_over_cap` the units over the cap; `scoreboard.dispatch_guard`, `startup` and `advisor`, `totals.advisor` and `skills[].missing` sum runs and sessions alike. Its units follow CR6's partition: a session's `skills`, `typed`, spend, `advisor`, `notes`, `refusals`, `context`, `tool_results` and `sweeps` hold only its transcript's rows outside every run window (the last three null on a run with no transcript window, and `context` alone null, with zero `tool_results` and `sweeps`, on a read unit with no main call of its own), while its `start`, `end`, `project`, `commands` and `title` are the whole transcript's, a title its runs share.
- Stored derived values (a unit's `merged`, `readable`, `firstSeenAt` and its warnings, with each warning's kind and step, the latest known winning) are written only by `applyVersion` in `packages/server/src/db/import.ts`, which both the import and `rebuildDerived` call, so a rebuild from `unitVersions` always gives the same rows; a new derived value goes there, and `main.ts` rebuilds them at every start. `mergeKnown` replaces the reporter's per-version maps (`COUNT_MAPS` in `packages/server/src/db/merge.ts`, sparse or fixed-key) whole when the new value isn't null, so a key a new version lacks stops counting, and when a version's `tool_results` isn't null, its `context`, `goal` and `spec` replace the stored ones, null included, since the reporter read the transcript.
- `units.missing_since`, `imports`, `state`, the app's finding labels (`finding_labels`) and the labeller's batches (`label_batches`) are stored facts, not derived: nothing in `unit_versions` can rebuild them, so a migration that drops or recreates their tables carries their values over.
- The reporter's cursor (`state`'s `cursor`, `getCursor`/`setCursor`/`clearCursor` in `db/read.ts`) is a stored fact, written only by `importReport` in the import's transaction from the export's `cursor`, and cleared by an export with none, so the next import resyncs in full; an export is incremental only when `isIncremental` holds for the cursor sent and the one returned (same state id, higher sequence), and then only its `removed` keys are marked missing; any other export is full, and every stored unit it lacks is marked missing.
- `runKey` and `sessionKey` in `packages/server/src/keys.ts` follow the reporter's `key` recipe (the first 16 hex of the SHA-256 of `date|project|branch`, and of `file`), since an incremental export's `removed` keys are matched against stored keys; check:real's `reporter keys` line compares them, counts only.
- The Anthropic API key and the labeller's settings live only in the data folder's `.env`, which the committed `.env.example` names and `process.loadEnvFile` loads. The key never reaches the repo (`.env` is git-ignored), a fixture, a log, an error text or the reporter's env. No test calls the API: the client is injected and stubbed, or `anthropicLabelClient` is pointed at a local stand-in through `ANTHROPIC_BASE_URL`. With no key, the labeller stays off.
- A label batch whose client throws stores nothing and is logged by `labelPending` as a `LabelError`'s message or else the error's name, never another error's text; the next batches still go. A label client's own failure message, fixed and with no finding text, is thrown as a `LabelError`.
- The labeller's daily max counts stored labels only (`labelledOn`), so a finding whose answer is dropped is sent again at every import, uncapped: `labelPending` sends each batch with one area's findings only, and the client builds its reply's schema and prompt from that area's ids, with `inArea` still the guard on what is stored.
- The app's finding labels show as the app's judgment, never as the reporter's facts. A workflow label, from the reporter, wins wherever both exist.
- Showing mode's scope is server state, through `packages/server/src/views/scope.ts`: a route builds it with `scopeOf` and passes it to its view, and only views apply it, with `showFacts`, `showWarning` and `maskText`; no route masks or filters. With a scope, every count includes every project and session (Home's step boxes' session warnings too) and only lists are filtered, Compliance's "other" rows aside. Each view's tests check with the leak check `leaks`, beside them, that a showing-mode response holds no hidden project's name, path or branch, and no session ID; `leaks` matches every key and string value of the response as sent, in any case as `maskText` masks, word fragments included, so a fixture's hidden folder or branch name must be no part, in any case, of a response key or of other fixture text; a hidden name equal to a fixed output string (a field, a path, a step kind, a category id) still counts as a leak, so no response key contains `main`, a branch most projects have (Models' `byPath`, the run page's `sessionModel`). A hidden string inside a shown folder name (`forbiddenStrings`' `shown`, the scope's `kept`) is neither masked nor a leak; a shown run's branch is masked like any text. The scope's hidden names (`scopeOf`, `forbiddenStrings`) are the folder names of every stored root not shown, runs' and sessions' alike (the sessions' through `storedSessionRoots` in `views/runs.ts`), and a session or its warning is listed with a scope only when `showSession` holds (its project's root is shown); a stored session warning's test of that is only `sessionWarningShown` in `views/runs.ts` (Home's feed, Compliance).
- `projectNames` in `packages/shared/src/projects.ts` is the one place a project's display name is made, with the config's `aliases` when given.
- `modelsCost` in `packages/shared/src/facts.ts` is the one cost of a `models` map (null with no map or no priced entry, else its priced entries' sum, through `addKnown`), for a run's facts (`runFacts`), the run page's phases (`views/run.ts`) and the Sessions view alike.
- A run's found findings (null before steps) and closed findings (acted on plus not acted on, null before steps) come only from `foundFindings` and `closedFindings` in `packages/shared/src/facts.ts`, for the run page's header, the Runs table and a change's totals (`views/work.ts`) alike.
- Migrations are generated with `drizzle-kit generate` from `packages/server/src/db/schema.ts` into `packages/server/drizzle/` and never hand-edited; SQL names are snake_case, times are `timestamp_ms` integers and JSON is `text` in `json` mode.
- Tests in any package read the invented fixtures, their JSON (`fixture`) or their file path (`fixturePath`), through `packages/shared/test/fixture.ts`, and every database test opens a fresh file in its own temp folder; a reporter export fixture is named `report-<name>.json`, so `reportFixtures` lists it for the tests that cover every export.
- A failure's error text (the reporter's, an import's, the labeller's) never quotes the reporter's stdout or the model's reply, which hold the data: it names the command, the exit and stderr's last line, the API's own error, or a fixed message; model calls go only through `anthropicLabelClient` in `packages/server/src/labeller.ts`, which turns the reply parser's errors into a fixed message.
- Background work runs through `createQueue` in `packages/server/src/queue.ts`, one queue per job named by its second argument (`import`, `label`), which logs a failing job under that name instead of rejecting, so a background error never crashes the server.
- An e2e axe check right after an animated change (a pressed switch, a dialog opening) first waits for that element's animations through `settled` in `packages/web/e2e/settled.ts`.
- A test file whose tests each start a Node process (`packages/server/test/check-real.test.ts`) raises its own timeout with `vi.setConfig`.
- A test that waits on an `fs.watch` event repeats the change inside `vi.waitFor`, since macOS can drop a change made right after the watch starts.
- Node runs the TypeScript sources directly with its built-in type stripping (Node >= 22.18, the `engines` floor), as in `check:real`: code stays erasable-only TypeScript (`erasableSyntaxOnly` in `tsconfig.base.json`), with no enums, namespaces or parameter properties.
- The server's request rules (the `Host` check, and for any method but GET and HEAD the `X-Dashboard-Refresh: 1` header and an allowed `Origin`) live only in `createApp`'s one middleware in `packages/server/src/app.ts`, which runs before every route; a route never checks them itself, and nothing sets an `Access-Control-*` header.
- API routes are added in `registerRoutes` in `packages/server/src/routes.ts`, one block per task; a POST-only route answers any other method with `postOnly` (405), and the server listens only through `serveApp`, on 127.0.0.1.
- Error text sent to the page goes through `trimPaths` in `packages/server/src/text.ts`, which cuts each absolute path to its last segment; the stored text stays whole.
- The app's finding labels are written only through `saveBatch`, and a label shown anywhere comes from `currentLabels`, both in `packages/server/src/db/labels.ts`, under the active list's number.
- The finding category list the app labels under (the active list) comes only from `activeList` in `packages/server/src/categories.ts`, built from the last good import's stored `categories`; with none, nothing is labelled and every finding is unlabelled, and a finding whose area has no categories in it is never sent or waiting (`labellable`).
- A label's `list_version` is 1 for the app's own list and 100 + N for the workflow's list version N; only the active list's number shows or is pending.
- API responses that show categories carry `categoryLabels` (each active-list id's label, from `categoryLabels` in `categories.ts`) for display; the web app holds no category list of its own.
- A page's API response is built by a pure function in `packages/server/src/views/<page>.ts` of the stored units, warnings, seen time and `now`, into its response type in `packages/shared/src/api/<page>.ts`; its route block only reads the database (`listUnits`, `listWarnings`, `getSeenAt`, `lastGoodImport`, `activeList`, `deps.now()`), parses the query and calls it.
- A week is named by its start date through `weekOf` in `packages/shared/src/week.ts`, as the reporter's `totals.weeks[].week`.
- A project is its root (`projectRoot` in `packages/shared/src/projects.ts`: the record's project with worktrees folded in) behind `projectKey` in `packages/server/src/keys.ts`; API responses carry the key and a display name (`storedFacts` in `views/runs.ts`), never the path. A stored run's root comes only from `rootOf` in `views/runs.ts` and a session's from `sessionRootOf` beside `projectRoot`, and a session's project key only from `sessionProjectKey` in `views/runs.ts` (null, "other project", unless its root is a stored run's).
- The weekly sums (runs by path, tasks, final review findings, fix rounds, stops, Fable and all points, cost, minutes per run, later fixes) come only from `weekSums` in `packages/server/src/views/home.ts`, as `WeekRow` from `packages/shared/src/api/weeks.ts`, for Home and the Weeks page alike, which check:real also compares with the reporter's `totals.weeks`; a new weekly sum goes there with its check.
- The weekly context sums (calls, tokens, largest, units over the cap, tool results by class, sweeps) come only from `contextSums` in `packages/server/src/views/context.ts`, the reporter's `context_rows`. A unit counts only with a `context`: a run in its record's week, a session in its start's. A week's mean and read share come only from `contextWeek` there, and a unit's read share only from `readShare` in `packages/shared/src/facts.ts`. `check:real` compares the sums with `totals.context`.
- A unit's week in a weekly sum over units (`contextSums`, `phaseSums`) comes only from `unitWeeks` in `views/runs.ts`: a run in its record's week, a session in its start's, a unit with no such time left out.
- Spend by phase is summed only by `phaseSums` in `packages/server/src/views/spend.ts`, over the units with a non-null `phases`, a run in its record's week and a session in its start's; a unit without counts in its week's `uncounted`, never filled from its `models`; a model the reporter has no price for stays null, and advisor cost stays outside every cost and share; a phase name no group holds is masked before the period's rows are summed.
- The Spend page's five groups are the app's, only in `SPEND_GROUPS` and `groupOf` beside `phaseSums`; a phase name the table doesn't hold counts under `unattributed`.
- A fixture's `phases` add up to its unit's `models` in cost and to its `advisor` in calls and cost.
- A run's or session's context facts (calls, median and largest tokens, calls past the cap, handoff, read share, sweeps) are made only by `contextFacts` in `packages/shared/src/facts.ts`, for `runView` (the run page's `context`, which adds `toolCharacters`) and `contextView` (which adds `overCap` and `handedOffTo`) alike; a unit's tool results summed over every class come only from `toolCharacters` there, which `readShare` uses too.
- The context cap the Context page draws is `CONTEXT_CAP` in `views/context.ts`, the app's default until the reporter exports its own (CR14), and the page says so.
- A median over the reporter's values is `median` in `packages/server/src/views/home.ts` (the reporter's `median_or_none`: known values only, null when none), and the reporter's coverage start is `coverageFrom` there, shown only through `CoverageNote` in `packages/web/src/home/WeeklyCharts.tsx`.
- A figure that isn't a sum over units comes from `lastGoodImport(db).totals`, which the route passes to its view as `totals`, and the view reads only through `reporterTotals` in `packages/shared/src/report.ts`; only the agents' mismatches, the main sessions' "differs" and stage table, the advisor's trial and weekly table, and Compliance's information lines are such figures. The response marks it with a literal `source: 'reporter'` inside a group of reporter figures (Models' `advisor.reporter`, Compliance's `information`) or `<figure>Source: 'reporter'` beside a single one (`mismatchesSource`, `stageSource`), and the page shows it with `reporterMark` (Compliance's information lines with `informationMark`), a figure null when `reporterTotals` returns null or lacks it. The units' advisor, refusals and startup are summed only by `unitSums` in `packages/server/src/views/steps.ts`, null only when `cr6Of` over every stored unit finds the export pre-CR6 (no session with `refusals`, no advisor with `by_role`), and startup null under a path filter.
- A view that needs a period's path and project filters without its finish-week check uses `period`'s `filters` in `views/runs.ts`, never its own path or project test.
- A skill's loads are summed only by `skillSums` in `packages/server/src/views/skills.ts`, the reporter's `skill_totals`; a view that shows names from units (skill names) masks them with `maskText` under a scope before summing, so sums still count every project; a skill's `missing` is summed only by `skillSums`' second pass (`missingFrom`, the period's units): runs' `missing_skills` and the units' `typed` triggers never met.
- Home's skills and commands are summed only by `usageSums` in `packages/server/src/views/home.ts`, over `periodUnits`' runs and sessions, its loads through `skillSums`: a command names a skill when its `commandSkill` (in `views/skills.ts`, the name after any `x:`; the Sessions timeline's `neverLoaded` uses it too) is a skill loaded or typed in any stored run or session (`skillNames`, so its kind is the same in every period), else it is a command row (`runs` and `typedNeverLoaded` null); a skill's sessions are those that loaded it, typed it or typed a command naming it; with a scope every name, commands' too, is masked with `maskText` before summing.
- The models by agent and path are summed only by `modelSums` in `packages/server/src/views/models.ts`, the reporter's `model_totals` (an agent `agent || 'general-purpose'`, a pair `${model || '-'}/${effort || '-'}`, as the reporter's `or`); with a scope, every name from units (agents, models, efforts, the advisor's roles and failed codes) is masked with `maskText` before summing, the advisor's through `unitSums`' `name` mapper.
- The run page's response is `runPageView` in `packages/server/src/views/run.ts`: `runView` (which the Findings view also calls, unchanged) plus the run's surroundings; its agents are `agentRows` (Models' rows) of `modelSums` over the run's dispatches through `maskModels`, and its offers' skills are masked only through `maskOffers` in `views/scope.ts`, the Steps page's too; a run's dispatches and `main` are masked only through `maskModels` in `views/models.ts` (Models' mapper), and a phase name only through `maskPhase` in `views/spend.ts` (a name `SPEND_GROUPS` holds as it is, any other through `maskText`).
- A step's model and effort are its tied dispatch's (the dispatch whose `step` is the step's index in the exported, unfiltered `steps`), else its own, field by field; made only in `runView`.
- The run graph's positions come only from `layout` in `packages/web/src/runs/flow.ts` (flat, wrapped or upright, by the panel's measured width), drawn by `RunFlow` with SVG paths and HTML buttons; React Flow isn't used there.
- The session graph's positions come only from `graphLayout` in `packages/web/src/work/graph.ts` (a session's column its distance from its chain's first session, a loop starting from its first node; an edge between lanes runs straight with rounded corners into its target's left side, a box's edges leaving one side at points spread along it), drawn by `SessionGraph` with `RunFlow`'s `BOX` classes and `pathOf` (its `elbow` form for `across` edges); lane labels follow the page: a goal's page labels every lane, a change's page none.
- The run page's selected step is its one filter: Problems, Strengths and Left for later follow it, and no Step select sits above them.
- A problems table's side is `PROBLEMS_SIDE` and a strengths table's `STRENGTHS_SIDE` (both in `format.ts`), as the table container's own 4 px left border, their empty line's panel too; an approved exception from the run page's captures to the kit's floor.
- The run page's other approved exceptions from its captures: a fix loop's arc reads "fix-checker ×2", and the step detail's column heads and found-nothing line join "agent · model, effort" through `stepBy`.
- A model/effort pair's cells come only from `pairsOf` in `format.ts` and `PairCells` in `components/Num.tsx`, for the Models page's agents and the run page's agents alike.
- Whether a finding's outcome takes the warning ink is only `outcomeWarns` in `format.ts`: the graph's chips, the step detail's Ended chip and Left for later alike.
- A run's timeline becomes the graph's boxes only through `stagesOf` and `unitsOf` in `packages/web/src/runs/flow.ts`; what a unit left is only `leftOf`, a stuck fix loop only `stuck`, and a unit's strengths only `strengthsOf`, all there.
- A session ID hidden while showing (`sessionId` null) is left out of an opened row: its fact returns null, in Sessions' ID and Context's "Its ID" alike.
- A stored session that another page names (Context's handoff, the run page's session and handoff) comes only from `shownSession` in `views/sessions.ts`: `sessionFacts`' title and ID while `showSession` holds, else null.
- A skill's outcome leaves the backend only as `skillOutcomeLabel`'s label in `packages/server/src/views/runs.ts`, since a string outcome is a file path; a counted outcome (a dict of numbers, simplify's `{applied, skipped}`) is "found something" when any count isn't 0, else "found nothing", as the reporter's `skill_totals` groups it, and its counts never leave the backend.
- A step kind's tokens and cost (`stepSums` in `views/steps.ts`) leave out a final review pair's second half (a dispatch's `pair`), as the reporter's scoreboard does, while `modelSums` and a step's tied dispatch keep it, as the reporter's `model_totals` and ties do; its cost is null until one of its dispatched models has a price, then the sum of the priced ones, through `addKnown` in `packages/shared/src/facts.ts` (the one sum that stays null until a value is known, `weekSums`' and `modelsCost`' too); its tokens are null until one of its dispatches carries `models`, priced or not; check:real compares step costs and tokens with a null read as 0 on both sides, since the reporter writes 0.0 and zeros where the dashboard writes null.
- A warning is current only while the latest export still reports it (a run's while its text is in the run's latest merged `warns`, a session's while the latest export holds the session and the text is in its latest `warns`), and only through `currentWarnings` in `views/runs.ts`; the stored `warnings` table supplies first-seen times, kinds and steps.
- A warning's family comes only from `FAMILIES` and `familyOf` in `packages/server/src/views/compliance.ts` ("other" for an unknown or null kind); with a scope, Compliance leaves out the "other" rows, its list leaves out "other" warnings and the session warnings `showSession` doesn't hold (as Home's feed does) and its `hidden` counts every warning in the period it left out of the list, and its information lines are left out whole and counted in `information.hidden`, never masked, since any line can name a project; its session warnings count in their first-seen week whatever the path and project filters, as Skills' session loads do.
- A query value becomes a step kind only through `toStepKind` in `packages/shared/src/report.ts`, as a path does through `toPath` and the Spend page's units through `toSpendUnits`.
- A finding or a reviewer's strength leaves the backend only as `runView` in `views/runs.ts` builds it, with its labels (the workflow's winning, the app's kept as `appCategory` and `appRelevance` only where it differs) and, with a scope, its masking; the Findings page's list and cells included.
- A list's `path`, `project` (a key) and `weeks` (default 4, at most 52) query params are parsed only by `periodQuery` in `packages/server/src/routes.ts`, and a view's period (its weeks, oldest first, and which runs it holds) comes only from `period` in `views/runs.ts` (a view that needs only its runs takes `periodRuns`'), a session is in a period only through `periodSessions` there, in the week of its `start` (none when it has no `start`), a view's runs and sessions together come from `periodUnits` there, or as stored units from `periodStoredUnits`, the one stored-unit period filter both `periodRuns` and `periodUnits` map to merged entries (filtered by `period`'s `filters`, a session's path null and its project key from its root only when that is a stored run's root, so a path filter leaves sessions out and a session-only root matches no project filter), Skills' loads aside, which still take every session, and a count record grows only through `addCount` there.
- The Sessions page's rows come only from `sessionsView` in `packages/server/src/views/sessions.ts`: a session holds the runs whose `window.transcript` is its `file`, a command is never loaded when an unmet `typed` trigger on the session or a held run has its skill (after any `x:`) and its time, and its path filter keeps a session holding a run of that path (`period`'s `filters` over the held runs as the response shows them), unlike the sums, where a path filter leaves sessions out; a session's title, ID and project name come only from `sessionFacts` there, for the Sessions and Context views.

- check:real compares each page's sum over units (`weekSums`, `runTime`, `stepSums`, `ruleSums`, `skillSums` with its missing counts, `modelSums`, `unitSums` for each figure it gives, `contextSums` by week against `totals.context`) over every run and session of the export with the reporter's matching all-time total, a missing count 0, a cost to the cent (a week's cost, as a step's, with a null read as 0 on both sides) and a share to 0.01 points; a line names the differing keys only when no project can name them (weeks, run time groups, step kinds, rules, unit figures), so skills and models print a count only, and a total the export lacks prints `not in the export`; its `reporter keys: N compared, M differ` line (`not in the export` when no unit has a `key`) compares the reporter's unit keys with `runKey` and `sessionKey`, a non-zero M meaning the key recipes drifted; its `phases: N compared, M differ` line compares each unit's phases with its `models` cost and its `advisor`, a count only. Its `work: 2 compared, N differ` line compares every stored unit's cost, to the cent, with the changes' plus the loose sessions' (`levels`) and with each goal's `goalView` cost plus No goal's, naming only `changes` or `goals`; its `work facts:` line counts the stored units carrying `headline`, `goal`, `spec` and `started_by`, and the `started_by` keys no stored session has; its showing check also fetches `/api/work` and each listed change's and goal's page.
- `importOnce` appends `--changed-since <getCursor or 0>` to the reporter command, so a command standing in for the reporter (dev:fixtures, tests) ignores extra arguments: `['sh', '-c', 'cat "$0"', file]`; check:real runs the plain command, which never touches the reporter's state.
- CI (`.github/workflows/ci.yml`) runs the same commands as local development, the screens through `pnpm test:screens`, whose container runs as `linux/amd64` everywhere so local baselines match CI's renders, on fixtures only and with no secret.
- The activity levels above a run are built only in `packages/server/src/views/work.ts`, with its response types in `packages/shared/src/api/work.ts`: a change is the units sharing a spec (its project and path, whichever projects they ran in), else a plan file, else one run; a session sits in one change at most (the reporter's spec, else the change of the newest run or plan record it holds, through `heldRuns` in `views/sessions.ts`, the Sessions view's map); a change's title, path, stage, projects and totals and a session's step (`stepOf`) are made there from reporter facts: a change's membership, goal, path and stage are never worked out from a branch, title or path, and its title falls back to its spec file's name (without date and `-design.md`), then to its run's branch; a view shows a change's title only through `changeTitle` there, which with a scope makes it from the change's runs in shown projects only, then masks it.
- A change's goal is its newest unit's goal, for every unit of it; a goal is a name, across projects, and "No goal" is a section with no page.
- On the Work page, filters choose which changes are listed and never cut a change's numbers; a goal section's totals are the sums of the changes it lists, so they can exceed Weeks' and Spend's over the same weeks.
- A goal's key is made from its name and a change's from its spec's project root and path (else its plan file, else its one run's `runKey`), by `keys.ts`' recipe; the reporter exports neither.
- Runs and Sessions are views of `/work` (`view=runs|sessions`), `/runs` and `/sessions` redirect there, and a session's link anywhere is `/work?view=sessions&session=<key>`; there is no session page.
- A session's link is `SessionLink` in `components/SessionLink.tsx`, named by its title, to `/work?view=sessions&session=<key>`.
- A goal section's title row on the Work page lines its totals up in columns shared by every section: the name's column `sm:w-64`, its chevron `RowToggle`'s `link` variant (the chevron alone the button, in primary ink, named by the link beside it), each total a `Pairs inline="columns"` pair as wide as its `TOTAL_WIDTHS` class from `sm` (`work/WorkPage.tsx`), its value at the column's end, the row wrapping under the name below `sm`; the totals sit on the backdrop, so none is muted and an unknown one is `Unknown backdrop`.
- A change's stage and a session's step show through `STAGE_LABELS` in `format.ts`.
- With a scope, a change is listed when its home project's root is shown (its spec's, else its one run's); its units in hidden projects count but are not listed and their projects show only as the "+N" count; on a goal's page, a session of a change of the goal that isn't listed counts but is not listed, as one in a hidden project, and a goal's name is a hidden string of the scope (`scopeOf`'s `goals`, `forbiddenStrings`' kind `goal name`, written "another goal" by `maskText`) when none of its homes (`goalHomes` in `views/work.ts`: its changes' home roots and its loose sessions' roots) is shown.
- A unit's change and goal as a view shows them come only from `listedChange` and `listedGoal` in `views/work.ts` (null when it has none or Work doesn't list it: a change by its home; a goal only while the unit's change is listed, else a loose session's own while `showSession` holds, whatever the goal's other homes); a session graph's edges come only from `sessionEdges` there (a `started_by` naming a stored session with a start, then a session's or held run's `context.handoff_to`, one edge per pair; a session whose `started_by` gives no edge has a hidden starter, never none); a session row's facts only from `sessionRow` in `views/sessions.ts`, for the Sessions and Work views alike.
- A run's change in the Runs view and on its page comes only from `runChange` in `views/work.ts` (`listedChange`, null for a change of that one run with no spec); a goal filter is only `inGoal` there (a unit's `goalOf`) and a Goal select's options only `goalOptions` there (each unit's `listedGoal`), for the Work, Runs and Sessions views alike.
- With a scope, a goal's or change's page answers only while Work lists it, else as a missing one, and a shown unit of an unlisted change shows no change or goal in its row.
