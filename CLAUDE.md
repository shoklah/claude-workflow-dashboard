# claude-workflow-dashboard

A live dashboard for the Claude Code agentic workflow (`shoklah/claude-workflow`, exported as `shoklah/claude-workflow-template`). It shows what the workflow's reporter, `scripts/workflow-report.py --json`, says about runs, steps, findings and spend.

This is a personal project, used as a playground for trying things and as a portfolio piece to show. The repo is public: it holds code and invented data only, and reads the real data at run time on the owner's machine. Design decisions are recorded in `docs/superpowers/specs/2026-11-09-live-dashboard-design.md`.

## Where freedom is allowed

- **Playground: technology choice, across the stack.** Frontend and backend frameworks, the ORM and migrations, charts, styling and build tooling are free ground for trying things. Each choice is recorded under `## Stack` below with one line on why.
- **Not playground: the data rules.** Privacy, facts only from the reporter, the server's `Host` checks, raw exports kept, and tests follow the workflow's rules (TDD, simplest first, reuse before writing, match the codebase), whatever the technology.

This repo is also the testbed for the workflow's design focus: design processes and skills are tried here first, and what earns its keep goes to the workflow repo as a change request.

## Stack

The stack is final; the component kit, the graphical libraries and the mockups keep evolving, one library per job at a time, and a swap is its own small task.

- **TypeScript end to end** (backend, frontend, import validation): one set of types runs from checking the reporter's JSON on import through the API to the charts, which guards "facts agree". The reporter itself stays Python, run as a separate process.
- **Final:** Node LTS, Hono, Drizzle over SQLite (`better-sqlite3`) with its migrations, zod, React with Vite, TanStack Query and Router, Tailwind, Vitest, Storybook, Playwright, pnpm workspaces (`shared`, `server`, `web`), GitHub Actions on fixtures only.
- **Evolving, current choice:** shadcn/ui for components (its Radix base, lucide icons and `cn` come with it), React Flow for the workflow diagram, ECharts for charts (through `echarts-for-react`), TanStack Table for tables (headless, so it renders into shadcn/ui's table with the API's own row types), `@axe-core/playwright` for the accessibility checks.
- **Labeller:** `@anthropic-ai/sdk` for the labeller's calls, through the official SDK.

## Design conventions

- Screens are agreed as mockups with invented data before the plan; the approved ones live in `docs/design/<date>-<topic>/`.
- Every component has Storybook stories on invented fixtures for its empty and full states, and a component that fetches data also for loading and error; a story with an interaction test is the UI's failing test.
- Screens are checked on fixtures with Playwright screenshot comparisons and axe accessibility checks.
- Charts are written with the `dataviz` skill loaded.

## Code conventions

- The data is personal (project paths, branch names, session IDs, costs, finding text): never commit real data, never put it in fixtures, never publish it publicly. Fixtures are invented.
- `workflow-report.py` is the only parser of the run log and the transcripts: when the dashboard needs a new fact, it goes to the workflow repo as a change request, never parsed here.
- This repo never edits the workflow repo or the template; they are a reference and the data source.
- Relative imports carry their `.ts` extension and type-only imports use `import type`; packages export their TypeScript sources, with no build step.
- The reporter's JSON schema lives in `packages/shared/src/report.ts`: every field is `.nullish()` (a `z.unknown()` one `.optional()`) unless the loader can't work without it; it validates the fields the dashboard reads plus those kept for slice 2's pages, any other field is left out, so it is stripped, and whether an unread field's drift should fail an import is the owner's call.
- A time from the reporter becomes a `Date` only through `parseTime` in `packages/shared/src/week.ts`, which reads a zone-less time as UTC as the reporter does, never through `new Date` or `Date.parse`.
- A fixture's `totals` agree with its runs and sessions by the reporter's rules (`week_rows`, `scoreboard`, `run_time`, `skill_totals`, `model_totals`, `advisor_facts`, `offer_totals`): for `weeks`, per week start date, `runs` by path and `cost` as the sum of the priced cost of the runs with `models`, null when none has them; `scoreboard.dispatch_guard`, `startup` and `advisor`, `totals.advisor` and `skills[].missing` sum runs and sessions alike. Its units follow CR6's partition: a session's `skills`, `typed`, spend, `advisor`, `notes` and `refusals` hold only its transcript's rows outside every run window, while its `start`, `end`, `project`, `commands` and `title` are the whole transcript's, a title its runs share.
- Stored derived values (a unit's `merged`, `readable`, `firstSeenAt` and its warnings, with each warning's kind and step, the latest known winning) are written only by `applyVersion` in `packages/server/src/db/import.ts`, which both the import and `rebuildDerived` call, so a rebuild from `unitVersions` always gives the same rows; a new derived value goes there, and `main.ts` rebuilds them at every start. `mergeKnown` replaces the reporter's count maps (`COUNT_MAPS` in `packages/server/src/db/merge.ts`) whole when the new value isn't null, so a key a new version lacks stops counting.
- `units.missing_since`, `imports`, `state`, the app's finding labels (`finding_labels`) and the labeller's batches (`label_batches`) are stored facts, not derived: nothing in `unit_versions` can rebuild them, so a migration that drops or recreates their tables carries their values over.
- The Anthropic API key and the labeller's settings live only in the data folder's `.env`, which the committed `.env.example` names and `process.loadEnvFile` loads. The key never reaches the repo (`.env` is git-ignored), a fixture, a log, an error text or the reporter's env. No test calls the API: the client is injected and stubbed, or `anthropicLabelClient` is pointed at a local stand-in through `ANTHROPIC_BASE_URL`. With no key, the labeller stays off.
- A label batch whose client throws stores nothing and is logged by `labelPending` as a `LabelError`'s message or else the error's name, never another error's text; the next batches still go. A label client's own failure message, fixed and with no finding text, is thrown as a `LabelError`.
- The labeller's daily max counts stored labels only (`labelledOn`), so a finding whose answer is dropped is sent again at every import, uncapped: `labelPending` sends each batch with one area's findings only, and the client builds its reply's schema and prompt from that area's ids, with `inArea` still the guard on what is stored.
- The app's finding labels show as the app's judgment, never as the reporter's facts. A workflow label, from the reporter, wins wherever both exist.
- Showing mode's scope is server state, through `packages/server/src/views/scope.ts`: a route builds it with `scopeOf` and passes it to its view, and only views apply it, with `showFacts`, `showWarning` and `maskText`; no route masks or filters. With a scope, every count includes every project and session (Home's step boxes' session warnings too) and only lists are filtered, Compliance's "other" rows aside. Each view's tests check with the leak check `leaks`, beside them, that a showing-mode response holds no hidden project's name, path or branch, and no session ID. A hidden string inside a shown folder name (`forbiddenStrings`' `shown`, the scope's `kept`) is neither masked nor a leak; a shown run's branch is masked like any text. The scope's hidden names (`scopeOf`, `forbiddenStrings`) are the folder names of every stored root not shown, runs' and sessions' alike (the sessions' through `storedSessionRoots` in `views/runs.ts`), and a session or its warning is listed with a scope only when `showSession` holds (its project's root is shown).
- `projectNames` in `packages/shared/src/projects.ts` is the one place a project's display name is made, with the config's `aliases` when given.
- Migrations are generated with `drizzle-kit generate` from `packages/server/src/db/schema.ts` into `packages/server/drizzle/` and never hand-edited; SQL names are snake_case, times are `timestamp_ms` integers and JSON is `text` in `json` mode.
- Tests in any package read the invented fixtures, their JSON (`fixture`) or their file path (`fixturePath`), through `packages/shared/test/fixture.ts`, and every database test opens a fresh file in its own temp folder.
- A failure's error text (the reporter's, an import's, the labeller's) never quotes the reporter's stdout or the model's reply, which hold the data: it names the command, the exit and stderr's last line, the API's own error, or a fixed message; model calls go only through `anthropicLabelClient` in `packages/server/src/labeller.ts`, which turns the reply parser's errors into a fixed message.
- Background work runs through `createQueue` in `packages/server/src/queue.ts`, one queue per job named by its second argument (`import`, `label`), which logs a failing job under that name instead of rejecting, so a background error never crashes the server.
- A test that waits on an `fs.watch` event repeats the change inside `vi.waitFor`, since macOS can drop a change made right after the watch starts.
- Node runs the TypeScript sources directly with its built-in type stripping (Node >= 22.18, the `engines` floor), as in `check:real`: code stays erasable-only TypeScript (`erasableSyntaxOnly` in `tsconfig.base.json`), with no enums, namespaces or parameter properties.
- The server's request rules (the `Host` check, and for any method but GET and HEAD the `X-Dashboard-Refresh: 1` header and an allowed `Origin`) live only in `createApp`'s one middleware in `packages/server/src/app.ts`, which runs before every route; a route never checks them itself, and nothing sets an `Access-Control-*` header.
- API routes are added in `registerRoutes` in `packages/server/src/routes.ts`, one block per task; a POST-only route answers any other method with `postOnly` (405), and the server listens only through `serveApp`, on 127.0.0.1.
- Error text sent to the page goes through `trimPaths` in `packages/server/src/text.ts`, which cuts each absolute path to its last segment; the stored text stays whole.
- The app's finding labels are written only through `saveBatch`, and a label shown anywhere comes from `currentLabels`, both in `packages/server/src/db/labels.ts`, under the active list's number.
- The finding category list the app labels under (the active list) comes only from `activeList` in `packages/server/src/categories.ts`, built from the last good import's stored `categories`; with none, nothing is labelled and every finding is unlabelled, and a finding whose area has no categories in it is never sent or waiting (`labellable`).
- A label's `list_version` is 1 for the app's own list and 100 + N for the workflow's list version N; only the active list's number shows or is pending.
- API responses that show categories carry `categoryLabels` (each active-list id's label, from `categoryLabels` in `categories.ts`) for display; the web app holds no category list of its own.
- A page's API response is built by a pure function in `packages/server/src/views/<page>.ts` of the stored units, warnings, seen time and `now`, into its response type in `packages/shared/src/api/<page>.ts`; its route block only reads the database (`listUnits`, `listWarnings`, `getSeenAt`, `lastGoodImport`, `activeList`, `deps.now()`), parses the query and calls it.
- A week is named by its start date through `weekOf` in `packages/shared/src/week.ts`, as the reporter's `totals.weeks[].week`.
- A project is its root (`projectRoot` in `packages/shared/src/projects.ts`: the record's project with worktrees folded in) behind `projectKey` in `packages/server/src/keys.ts`; API responses carry the key and a display name (`storedFacts` in `views/runs.ts`), never the path. A stored run's root comes only from `rootOf` in `views/runs.ts` and a session's from `sessionRootOf` beside `projectRoot`, and a session's project key only from `sessionProjectKey` in `views/runs.ts` (null, "other project", unless its root is a stored run's).
- The weekly sums (runs by path, tasks, final review findings, fix rounds, stops, Fable and all points, cost, minutes per run, later fixes) come only from `weekSums` in `packages/server/src/views/home.ts`, as `WeekRow` from `packages/shared/src/api/weeks.ts`, for Home and the Weeks page alike, which check:real also compares with the reporter's `totals.weeks`; a new weekly sum goes there with its check.
- A median over the reporter's values is `median` in `packages/server/src/views/home.ts` (the reporter's `median_or_none`: known values only, null when none), and the reporter's coverage start is `coverageFrom` there, shown only through `CoverageNote` in `packages/web/src/home/WeeklyCharts.tsx`.
- A figure that isn't a sum over units comes from `lastGoodImport(db).totals`, which the route passes to its view as `totals`, and the view reads only through `reporterTotals` in `packages/shared/src/report.ts`; only the agents' mismatches, the main sessions' "differs" and stage table, and the advisor's trial and weekly table are such figures. The response marks it with a literal `source: 'reporter'` inside a group of reporter figures (Models' `advisor.reporter`) or `<figure>Source: 'reporter'` beside a single one (`mismatchesSource`, `stageSource`), and the page shows it with `reporterMark`, a figure null when `reporterTotals` returns null or lacks it. The units' advisor, refusals and startup are summed only by `unitSums` in `packages/server/src/views/steps.ts`, null only when `cr6Of` over every stored unit finds the export pre-CR6 (no session with `refusals`, no advisor with `by_role`), and startup null under a path filter.
- A view that needs a period's path and project filters without its finish-week check uses `period`'s `filters` in `views/runs.ts`, never its own path or project test.
- A skill's loads are summed only by `skillSums` in `packages/server/src/views/skills.ts`, the reporter's `skill_totals`; a view that shows names from units (skill names) masks them with `maskText` under a scope before summing, so sums still count every project; a skill's `missing` is summed only by `skillSums`' second pass (`missingFrom`, the period's units): runs' `missing_skills` and the units' `typed` triggers never met.
- Home's skills and commands are summed only by `usageSums` in `packages/server/src/views/home.ts`, over `periodUnits`' runs and sessions, its loads through `skillSums`: a command names a skill when its `commandSkill` (in `views/skills.ts`, the name after any `x:`; the Sessions timeline's `neverLoaded` uses it too) is a skill loaded or typed in any stored run or session (`skillNames`, so its kind is the same in every period), else it is a command row (`runs` and `typedNeverLoaded` null); a skill's sessions are those that loaded it, typed it or typed a command naming it; with a scope every name, commands' too, is masked with `maskText` before summing.
- The models by agent and path are summed only by `modelSums` in `packages/server/src/views/models.ts`, the reporter's `model_totals` (an agent `agent || 'general-purpose'`, a pair `${model || '-'}/${effort || '-'}`, as the reporter's `or`); with a scope, every name from units (agents, models, efforts, the advisor's roles and failed codes) is masked with `maskText` before summing, the advisor's through `unitSums`' `name` mapper.
- A skill's outcome leaves the backend only as `skillOutcomeLabel`'s label in `packages/server/src/views/runs.ts`, since a string outcome is a file path.
- A warning is current only while the latest export still reports it (a run's while its text is in the run's latest merged `warns`, a session's while the latest export holds the session and the text is in its latest `warns`), and only through `currentWarnings` in `views/runs.ts`; the stored `warnings` table supplies first-seen times, kinds and steps.
- A warning's family comes only from `FAMILIES` and `familyOf` in `packages/server/src/views/compliance.ts` ("other" for an unknown or null kind); with a scope, Compliance leaves out the "other" rows, its list leaves out "other" warnings and the session warnings `showSession` doesn't hold (as Home's feed does) and its `hidden` counts every warning in the period it left out of the list; its session warnings count in their first-seen week whatever the path and project filters, as Skills' session loads do.
- A query value becomes a step kind only through `toStepKind` in `packages/shared/src/report.ts`, as a path does through `toPath`.
- A finding or a reviewer's strength leaves the backend only as `runView` in `views/runs.ts` builds it, with its labels (the workflow's winning, the app's kept as `appCategory` and `appRelevance` only where it differs) and, with a scope, its masking; the Findings page's list and cells included.
- A list's `path`, `project` (a key) and `weeks` (default 4, at most 52) query params are parsed only by `periodQuery` in `packages/server/src/routes.ts`, and a view's period (its weeks, oldest first, and which runs it holds) comes only from `period` in `views/runs.ts` (a view that needs only its runs takes `periodRuns`'), a session is in a period only through `periodSessions` there, in the week of its `start` (none when it has no `start`), a view's runs and sessions together come from `periodUnits` there (filtered by `period`'s `filters`, a session's path null and its project key from its root only when that is a stored run's root, so a path filter leaves sessions out and a session-only root matches no project filter), Skills' loads aside, which still take every session, and a count record grows only through `addCount` there.
- The Sessions page's rows come only from `sessionsView` in `packages/server/src/views/sessions.ts`: a session holds the runs whose `window.transcript` is its `file`, a command is never loaded when an unmet `typed` trigger on the session or a held run has its skill (after any `x:`) and its time, and its path filter keeps a session holding a run of that path (`period`'s `filters` over the held runs as the response shows them), unlike the sums, where a path filter leaves sessions out.
- A table row that opens a detail row below it names its toggle as a `button` with `aria-expanded` in its first cell, the detail a full-width row (`colSpan`) shown only while open (`SessionRows` in `packages/web/src/sessions/SessionsTable.tsx`).
- The web app reads the API only through `src/api.ts` in `packages/web`: `useStatus` for the import's status, `useLiveQuery` for every page's data (its key holds the last good import's time, so data refetches in place when an import lands), and `refresh`, `markSeen` and `showProjects` for the POSTs, which share its one `post` helper.
- shadcn/ui components are added with its CLI (`packages/web/components.json`) into `src/components/ui/`; its `@/` alias is for the CLI and the files it writes, and the app's own code imports them relatively, with their extension.
- shadcn's `Table` forwards `containerProps` to its scroll container, the one hand edit in `src/components/ui/`; a table that scrolls sideways passes `tabIndex: 0`, `role: 'region'` and an `aria-label` through it.
- Stories get the app's providers (a query cache without retries, tooltips, a memory router on `/` or the story's `parameters.path`) from `.storybook/preview.tsx`, and stub the API with `mockApi` from `src/test/mock-api.ts` in their `beforeEach`; the web package's other tests are `src/**/*.test.tsx`, run in chromium like the stories.
- `@cwd/shared` runs in the browser and in Node, so it imports no `node:` module; Node-only code (run and session keys, `keys.ts`) lives in `packages/server`, and the web app imports shared types and values from `@cwd/shared`, never by relative path.
- A page that fetches takes what its route gives it (a run's key) as a prop, so its stories render it without route params.
- Story fixtures a screen's stories share are invented API responses in `packages/web/src/test/<screen>.ts`.
- The web app's display formatting (costs, durations, plurals, step names, "project · branch") lives in `packages/web/src/lib/format.ts`, one function or map per fact on every screen (`STEP_LABELS` for step kinds); a fact that isn't known shows as its `NONE`, "–", and a duration is rounded to whole minutes first, then shown as "25 min" or "2 h 10".
- Counts by key show through `countsLabel` in `format.ts` (zeros kept, an unknown count as `NONE`), and a week's breakdowns (runs by path, findings by severity) through `nonZeroCountsLabel`, as the approved basics mockup writes them: "small 4 · full 2", "none" when all are 0; both join through `joined`.
- A finding's category shows through `categoryLabel(category, labels)` in `packages/web/src/lib/format.ts`, named by the response's `categoryLabels` (its id when they don't name it, "unlabelled" when null), a set category in `CategoryBadge`'s outline badge (`runs/FindingsTable.tsx`), dashed and titled "The app's label" only on the app's labels (`judge: 'app'`).
- The Findings grid's "N · M by the app" split, and its categories out of the app's dashed badge, show only once a finding of the period shows the workflow's label (`workflowLabelled` in `packages/web/src/findings/FindingsGrid.tsx`); until then the page's one line says every label is the app's.
- A reporter-sourced figure shows `reporterMark` only through `ReporterMark`'s dashed outline badge (`src/components/ReporterMark.tsx`), titled by its tooltip.
- A list page's path, project and period filters and its API path come from `ListFilters` and `listPath` in `packages/web/src/runs/RunsPage.tsx`; a page adds its own controls as `ListFilters`' children.
- A page's switch (a measure, an area) is a `role="group"` of `Option`s (`findings/FindingsPage.tsx`: shadcn `Button`s with `aria-pressed`); an option not available yet is a disabled one inside a focusable span, so its tooltip still opens.
- Charts use ECharts with the SVG renderer and no animation, the dataviz reference palette's light slots in fixed order, a `role="img"` container with an aria-label, and a table view of their numbers.
- A heatmap is `HeatmapTable` in `packages/web/src/components/HeatmapTable.tsx`, an HTML table with each cell's number written in it, so it is its own table view, its cells shaded only through `cellShade` in `format.ts` (the dataviz blue ramp, a grey for 0); a row's `id` (a category or kind, `''` for none) identifies it in the selection and its `name` labels its cells.
- A share bar is a one-hue meter, `SHARE_FILL` on its same-ramp track `SHARE_TRACK` (both in `format.ts`, taken from the heatmap's `SHADES` ramp), with its percent written beside it.
- A warning's kind shows through `kindLabel` (`KIND_LABELS`, the slug with spaces for a kind it doesn't hold, "other" when null) and its family through `FAMILY_LABELS`, both in `format.ts`.
- A warned element's orange is `WARNING_BORDER` (the dataviz status orange) for its border and `WARNING_INK` for its text, both in `format.ts`, and always comes with a written count or word, never colour alone.
- dev:fixtures saves `packages/shared/fixtures/labels.json`'s invented labels (model `fixture`) through `saveBatch` under the active list (the last fixture's), each naming its run by date and branch; an entry that matches no finding, or whose category isn't one of the list's ids for the finding's area, stops it.
- Playwright's `checks` are `packages/web/e2e/*.spec.ts` (axe and behaviour, anywhere); its `screens` are `e2e/*.screens.ts`, run only by `pnpm test:screens` in the container, with their baselines committed; every e2e test pins the browser clock with `pinClock` to dev:fixtures' time, and the server listens on `E2E_PORT` (default 4399), so worktrees run their checks side by side; `pnpm test:screens` takes file filters only after a self-contained option (`pnpm test:screens --workers=1 e2e/<page>.screens.ts`), since the script ends in `--project screens`.
- The launchd agent's plist comes only from the pure `plist()` in `packages/server/src/agent.ts`; it runs `src/main.ts` with the absolute `node` that ran `pnpm agent:install`, since there is no server bundle (the root `build` builds only the web app `main.ts` serves), and no test writes to `~/Library/LaunchAgents` or runs `launchctl`.
- check:real's showing check imports into a fresh database in a temp folder, never the data dir's, and prints only `showing: pass` or a leak count; the app's errors there go to its catch (`onError` rethrows) and print a fixed message, since Hono's default error log and a query's error text can quote the data.
- check:real compares each page's sum over units (`weekSums`, `runTime`, `stepSums`, `ruleSums`, `skillSums` with its missing counts, `modelSums`, `unitSums` for each figure it gives) over every run and session of the export with the reporter's matching all-time total, a missing count 0, a cost to the cent and a share to 0.01 points; a line names the differing keys only when no project can name them (weeks, run time groups, step kinds, rules, unit figures), so skills and models print a count only, and a total the export lacks prints `not in the export`.
- CI (`.github/workflows/ci.yml`) runs the same commands as local development, the screens through `pnpm test:screens`, whose container runs as `linux/amd64` everywhere so local baselines match CI's renders, on fixtures only and with no secret.
